# IFEval browser V1: public provenance and reproduction

Authorship: [Arhaan Aggarwal (Arhaan2)](https://github.com/Arhaan2).
The [canonical closeout](../reports/ifeval-browser-v1-final/README.md) records a completed, manually continued experiment with inconclusive held-out compliance: 70/128 candidate versus 69/128 baseline, +0.78125 percentage points, frozen paired 95% interval −5.47 to +7.03 points. Improvement and equivalence are unestablished. This document describes saved evidence and future reproduction; it is not an instruction to start another run.

## Exact intervention and artifact identities

The pristine source is [Qwen/Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B/tree/2fc06364715b967f1860aea9cf38778875588b17), revision `2fc06364715b967f1860aea9cf38778875588b17`. Starting from that pristine snapshot, apply `scale_columns` with factor **0.75** to columns **0–59 inclusive**, across all 1,024 rows, in each of these BF16 matrices, in the listed order:

1. `model.language_model.layers.15.mlp.down_proj.weight`, shape `[1024,3584]`.
2. `model.language_model.layers.19.mlp.down_proj.weight`, shape `[1024,3584]`.

No direction-removal operation or earlier candidate composition was used. The existing checkpoint editor decodes to binary64, multiplies, and rounds directly to BF16 with round-to-nearest/ties-to-even after each operation, without intermediate float32 rounding. Preserve the complete snapshot's other files and tensor bytes. The implementation is [checkpoint_numeric.py](../weight_space_lab/checkpoint_numeric.py) and [checkpoint.py](../weight_space_lab/checkpoint.py); this is a deterministic replay of the saved transformation, not a new proposal.

## Quantization audit

Both arms use `q4f16_1`, groups of 32 input-column coordinates, uint32 packed weights (eight little-endian nibbles per word), float16 scales, and decoding `float16((uint4 - 7) * float16_scale)`. The selected columns occupy groups 0 and 1 (columns 0–63), so columns 60–63 share a group with edited coordinates even though their source values were unchanged.

Selection preceded new model outputs: seed 42, stable SHA-256 ordering on `{seed,item_id}`, rare-type coverage followed by balanced coverage with unique normalized available tasks. There were 10,410 eligible Ai2 rows and 344 eligible Google prompts; the remainder were excluded or quarantined. Both selected sets cover 18 supported instruction types and eight families. [ifeval_data.py](../weight_space_lab/ifeval_data.py) defines the mapping and feasibility rules. Ai2 integer “at most N” maps to official “less than N+1”; unsupported or ambiguous records are excluded as whole records. Manual task-only exclusions and exact/normalized overlap evidence remain private. Consequently the IDs, rather than rerunning selection without those private exclusions, specify the released evaluation schedule. Derived-task comparison does not prove absence of paraphrase overlap or pretraining exposure. V1's 128 prompts are now exposed.

It covers wrapper/worker source, upstream assets, Python version and dependency pins, not just the Google Git commit. Actual evaluator Python was **3.13.5**, NumPy **2.3.5**; data preparation used PyArrow **19.0.1** and tokenizers **0.22.2**. IFEval dependencies were absl-py 2.5.1, langdetect 1.0.9, nltk 3.10.4, immutabledict 4.3.1, six 1.17.0, defusedxml 0.7.1, click 8.5.1, joblib 1.6.0, regex 2026.11.7, tqdm 4.70.1 and cloudpickle 3.1.2. All upstream checker-file hashes are pinned in [grading.py](../weight_space_lab/grading.py). Python random and language detection use seed 0; the language label itself was not retained.

Scoring retains failed and truncated outputs. The frozen `think_tags` policy extracts the answer after the leading complete thinking block; it does not repair, rewrite, or retry responses. Each grader call has a 20-second ceiling and no retries. Prompt accuracy requires all instructions; instruction accuracy divides compliant constraints by scheduled constraints. The uncertainty analysis is the frozen 10,000 paired percentile bootstrap samples, seed 0, lexicographic item-ID order, NumPy's default linear quantiles. Whole prompts are clusters, with instruction ratios recalculated in every resample. No new primary score or exact significance test was introduced.

## Runtime and session history

BrowserLLM base is [gufranmirza/browser-llm-bench](https://github.com/gufranmirza/browser-llm-bench/tree/b39187b1aff1f218493622d7fcf3cd5d24773b41), revision `b39187b1aff1f218493622d7fcf3cd5d24773b41`. The source patches are `browser-integration-v2.patch`, then `ifeval-browser-v1.patch`, then `ifeval-heldout-schedule.patch`; the separate continuation adds `ifeval-heldout-continuation.patch`. Earlier task-mode patches are historical alternatives, not additional patches to stack onto integration v2.

Every scored request uses a fresh conversation, thinking disabled, temperature 0, top-p 1, seed 42 reset per request, effective context 4,096, maximum output 1,024, presence/frequency penalties 0, repetition penalty 1, `n=1` and `ignore_eos=false`. Each engine session has one separately recorded 16-token application warm-up. The fixed warm-up and chat rendering are in the released adapter source. Four injected empty-thinking IDs count toward the cap but are excluded from sampled completion usage, giving ceilings of 1,020 sampled scored tokens and 12 sampled warm-up tokens. Request timeout is 120 seconds; an interrupted request that does not settle within 10 seconds triggers worker termination. No automatic retries occur.

Other host activity, browser/driver variation, cache/load behavior, sampled telemetry and the candidate's separate continuation prevent a controlled speed or energy claim.

One manual editor proposal was accepted. Development selection required complete execution/cleanup and resolved grading on all 32 fixed items, and strictly greater strict prompt compliance; ties retained pristine. Candidate 17/32 versus baseline 16/32 selected the candidate. Loose prompt and instruction results were 18/32 versus 17/32; strict instruction results were 17/32 versus 16/32. The sole strict/loose gain satisfied a highlights checker through repetitive content. The subsequent held-out result, not that development improvement, is the completed 70/128 versus 69/128 comparison.

Preserved failures are part of the history. The first conversion stage stopped at a package precheck because the launcher dereferenced the virtual-environment interpreter symlink to system Python. No converter subprocess or candidate generation ran in that attempt. A separately recorded helper repair preserved the interpreter's environment, followed by one manual conversion continuation using the already imported checkpoint. The original failure, failed offline cache probe, verification revisions and closed import ledger remain preserved; they are not successful conversions or new proposals.

Held-out execution ran pristine first, then candidate. The candidate stopped after 94 scored outputs because the supervisor snapshot had not reconciled the durable predecessor completion when gating position 95. Evidence supports a snapshot/intent race; exact snapshot-read timing was not instrumented. Positions 95–128 had no acknowledgement, reservation or model call. Forced termination closed owned processes; graceful unload was unconfirmed. A new, separately budgeted session with its own warm-up completed only the 34 undispatched suffix positions using the supervisor repair. The join preserved all original 128 baseline and 94 candidate grades and added 34 new candidate grades. It did not regrade or reopen old ledgers. Technical completion therefore means **complete_manually_continued**, not completion of the original uninterrupted protocol. Session and cumulative costs remain in the canonical report.

The experimental editor workflow used a private development packet and manual returned-JSON import with request-digest/base binding, a seven-day ingestion window, one consumed submission slot, and saved-checkpoint validation. It was requested as Astra/Ultra; observed provider model/version, accepted effort, per-request usage and billing were unavailable. Model self-description and a matching response envelope are not independent identity authentication. Reported proposal provenance says file-reading and JSON-parsing tools ingested the development packet, with no external research, additional weight inspections or target forward passes; this was not independently observed. It was not tool-free. Editor isolation and denial of unrelated files/tools were unverified; no isolated-editor or causal-column claim follows. Prior interface audits remain historical evidence, not proof of present enforcement.

## Reproduction scope and procedure

The release supports inspection of the transformation and frozen implementations, reconstruction of the exact selected public dataset rows from their source IDs, arithmetic comparison of saved sanitized results, and offline mechanics tests. It preserves the failed-stage reports alongside the completed result. It does **not** include model/checkpoint binaries, the deployed WASM and shard payloads, private prompts/response logs, editor packet/response envelopes, authorization text, SQLite ledgers, process dumps or local machine paths. A hash identifies retained evidence; it does not make unavailable bytes recoverable. Saved public summaries cannot independently establish the grader's correctness on withheld raw responses or prove editor identity/access boundaries.

For a future independent reconstruction, use a fresh output tree and retain all attempts:

1. Obtain the pinned upstream Qwen snapshot and source datasets under their upstream terms. Inventory source filenames and bytes with `inventory_model`; compare the source identity before editing. Read Ai2 rows by zero-based parquet index and map `ground_truth` with `ifeval_data.map_ground_truth`; read Google rows by original `key` retaining original prompt, instruction IDs and kwargs. Follow the released ID order without rerunning the selection heuristic. Use the pinned tokenizer and `ifeval_data.input_tokens` to check every rendered length and the 4,096-token context constraint.
2. Replay only the two documented scaling operations through `CheckpointEditor.propose` with the existing policy and `provenance: editor_proposal` for this historical transformation. Independently call `verify_candidate`; check stored-change counts, per-tensor hashes and complete candidate source identity. This step requires the acquired snapshot and explicit execution scope; it was not performed during closeout.
3. Recreate the pinned converter environment and obtain the identical model library. Use the repaired interpreter helper in `browser_candidate_recovery`, the existing converter and `browser_candidate` packaging/audit. A recovery record used by that historical entry point binds its particular preserved failure; do not fabricate it for a new run. Bind a new run's provenance to the reused helper under a separately specified protocol. Compare source/deployment identities and all decoded-change counts. The release supplies code and expected identities, not a ready-to-run private conversion manifest.
4. In a clean checkout of the pinned BrowserLLM base, apply the patch sequence above and build using its lockfile. For an independently authorized rerun, create fresh runtime manifests and ledgers, retain all fixed settings and dataset order, and verify actual fetched model/runtime bytes. The original held-out and continuation manifests are historical, single-use inputs and cannot be reused to gain execution capacity. A clean rerun need not induce the historical supervisor failure, and therefore is a fresh comparison rather than an exact replay of the original session timeline.
5. For preserved-evidence verification, a custodian possessing the private evidence can run `python3 scripts/verify_ifeval_continuation.py --root <preserved-continuation-root> --check-only`. It reads original bytes and immutable ledgers and does not load a model or call the grader. Full private paths must resolve as preserved; this is not a released-only command. New analysis copies must use fresh destinations. Do not invoke generation, conversion or grading during a saved-result audit.

The exact grader-wrapper hash depends on Python 3.13.5 and pinned source/package identities. Different hardware, browser/runtime bytes or numerical libraries may change outputs or timing; equality of temperature and seed alone does not guarantee byte-identical responses. Reproducing the private selection/exposure audit, independently checking all original grades and reconstructing original session/authorization history require custodian access to those retained records. Reproducing the frontier editor's proposal process is not supported by the release because its immutable model identity and enforced access boundary were not observed.
