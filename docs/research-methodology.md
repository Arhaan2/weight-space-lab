# Weight Space Lab: research methodology

Maintainer: [Arhaan Aggarwal (Arhaan2)](https://github.com/Arhaan2). Updated November 10, 2026.

The research question is whether a frontier model can propose a small, explicit edit to another model's weights that improves instruction following while preserving or reducing its browser resource use. This release separates historical V1 quality evaluation, the completed V2 development search, the first all-edit resource pilot, and a new six-version comparison with a freshly measured baseline and a fourth actual Astra proposal. A smaller output-token count is an observation, not proof of lower memory, computation or energy. The joint objective requires evidence for both quality and resources.

## Studies and hypotheses

| Study | Comparison and experimental unit | Status and inference scope |
| --- | --- | --- |
| V1 development | Pristine versus one edit; the same 32 development prompts | Strict compliance 16/32 versus 17/32. Development evidence informed the experiment; it is not untouched confirmation. |
| V1 final evaluation | Pristine versus the frozen V1 edit; 128 paired prompts containing 173 instructions | Completed with a documented manual continuation. Strict compliance 69/128 versus 70/128; difference +0.78125 percentage points, paired 95% interval −5.46875 to +7.03125 points. Improvement and equivalence are unestablished. |
| V2 development | Three adaptive proposals, each evaluated on the same 32 prompts against a saved pristine baseline | Every candidate scored strict 16/32 and loose 17/32. None qualified under the frozen strict-gain rule. No untouched final set was available. |
| All-edit resource pilot | Pristine, V1 edit and all three V2 edits; two browser sessions per artifact | A separate resource-only study. Quality qualification is not required. Run status and measurements are reported in its own result file; this document is not evidence that scheduled sessions completed. |
| Fresh six-version comparison | Pristine, V1, Astra rounds 1–3 and one new round 4; the same 32 exposed development prompts and two resource sessions per artifact | A separately frozen current-browser cohort. The first five quality results inform the one new proposal. Every technically valid version receives resource measurement regardless of score. Actual completion and observations are recorded in the fresh report. |

The quality hypothesis is higher strict prompt-level IFEval compliance. V2 required more than 16/32 strict passes, at most 13,941 scored output tokens and complete technical validation; pristine wins a quality tie. Its selection rule has already closed with pristine retained. The resource pilot asks how the five deployed artifacts behave on one fixed workload in the same current environment. It neither reopens V2 selection nor changes historical outcomes. Resource changes cannot establish preservation of quality on an untouched task set.

## Model and intervention

All artifacts derive from [Qwen/Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B/tree/2fc06364715b967f1860aea9cf38778875588b17), source revision `2fc06364715b967f1860aea9cf38778875588b17`. The pristine source manifest identity is `f3272ddbea59cc854268e91e387416cd84a633a97ae7d9cfaa1325890eac602d`. Its inventory contains 873,438,784 stored coordinates, including aliases and buffers; this is not a count of independent trainable parameters. The MLC deployment uses the text backbone and excludes vision and MTP.

The saved deployed configuration records 24 layers, hidden width 1,024, MLP width 3,584, eight attention heads, two key/value heads and full-attention interval four. Architecture, tokenizer, conversation template and compiled library remain fixed. Inference uses WebLLM 0.2.86, WebGPU and MLC `q4f16_1`. The model-library SHA-256 is `023c24d853746e24599dc99d7649e356986fd3e1c476e6a2b8ef7af4c9f056e0`; tokenizer SHA-256 is `5f9e4d4901a92b997e463c1f46055088b6cca5ca61a6522d1b9f64c4bb81cb42`.

Each edit scales 60 input columns across all 1,024 rows of each of two BF16 matrices: `model.language_model.layers.15.mlp.down_proj.weight` and `model.language_model.layers.19.mlp.down_proj.weight`. Every proposal starts independently from pristine; the V2 rounds are not cumulative checkpoint updates.

Each edit changes 122,880 stored and numerical source entries. The V2 allowed family fixed these two matrices, permitted a contiguous 60-column block beginning at 0–3524, and allowed factors 0.5, 0.75, 1.25 or 1.5. Saved operations, source audits and conversion audits determine what actually changed. The editor multiplies in binary64 and rounds directly to BF16 with round-to-nearest/ties-to-even. Quantization uses groups of 32 columns, so a changed group scale can alter decoded values outside the exact source columns. Such effects are audited rather than treated as additional source interventions. Hashes here identify complete manifests, not individual weight files.

This intervention changes values, not tensor shapes, parameter count, bit width or the compiled computation graph. It does not introduce a smaller architecture or a sparse inference kernel. A resource difference may arise through changed output length or runtime behavior; unchanged architecture alone neither proves measured resource equality nor explains an observed timing difference.

V2 used three actual fresh-context collaboration agents requested as `gpt-6-astra`, without a reasoning-effort override. No Ultra or immutable provider-version claim is made. Technical isolation was unverified in both workflows.

The development packet supplied approved weight information, the 32 development tasks, saved pristine outputs and grades, the response schema and the quality/resource objective. Later V2 packets also supplied preceding candidate feedback: compliance, paired changes, outputs, tokens, truncations and available timing/resource limitations. This is one adaptive search trajectory, not three independent editor replications. Round 3 required a second delivery turn to read the same packet after tool-output truncation; it produced one proposal without new scientific feedback. There were three V2 agents, four delivery turns and three proposals. Provider token usage and billing are unavailable.

## Fresh baseline and Astra round 4

The new cohort reran pristine, V1 and all three existing Astra artifacts before the fourth proposal. All five reproduced their earlier strict/loose scores and output-token totals under the newly frozen Chrome 157 environment. Strict counts were 16, 17, 16, 16 and 16 of 32; the new proposal's primary target is to exceed both pristine and the best prior artifact. Equal or fewer output tokens than fresh pristine is a secondary target. It does not decide resource eligibility.

One fresh-context collaboration agent was requested as `gpt-6-astra`, without a reasoning-effort override. Its indexed packet supplied all 160 fresh observations, their official grades and token counts, the approved pre-existing weight statistics, and explicitly separated historical resource feedback. All 33 parts of the 389,782-byte packet were supplied, with exact concatenation and hashes checked. Earlier proposal rationales were unavailable; none were invented retrospectively. The fourth agent supplied one response and a separate 140-word decision summary before its new weights were built or evaluated. The original text and hashes remain preserved as a pre-evaluation prediction.

Round 4 scales columns 0–59 of both designated matrices by 0.5 from pristine. Its audited source identity is `c10759a31f22f980c56cb2e959b4d7355a00f7181df7fd57ba8d3e9ae9b3f1c3`. Exactly 122,880 stored and numerical entries changed; 486 other tensors remain unchanged. Source, quantization and packaging audits passed. This is a stronger dose on V1's support, not a cumulative edit to the V1 checkpoint. Provider-side immutable model identity, accepted effort, token usage, billing and technical isolation remain unverified or unavailable.

The new candidate scored strict 16/32 and loose 17/32, with 16,998 sampled output tokens and 16 truncated responses. Fresh pristine scored 16/32 and 17/32 with 13,941 tokens and 12 truncations; V1 remained best at 17/32 strict. Round 4 had three improved, three regressed and 26 tied prompt outcomes versus pristine under both strict and loose scoring. It therefore failed both strict-gain targets and used 21.93% more output tokens. This negative result is retained and does not prevent resource measurement. It is a result on the exposed development set, not a generalization estimate.

All twelve resource sessions completed without target failures or retries. The fresh pristine and round-4 equal-weight response means were 612.88 and 737.83 ms/request (+20.39%); their mean sampled native peaks were 2.990 and 3.062 GB (+2.41%). Round 4 generated 2,880 tokens per 60-request session versus 2,340 for every other version (48 versus 39 tokens/request). Its mean full-response throughput was 65.06 versus 63.64 tokens/s (+2.23%). These simultaneous observations distinguish response length and duration from per-token speed; they do not establish a causal efficiency improvement. GPUBuffer descriptor and WASM address-space maxima were identical, while power remained unavailable. All individual session values, including the resource variation across the mirrored schedule, remain in the report and interactive figure.

The resource order is pristine, V1, rounds 1–4, then the reverse. Each session follows the same 60-request standard workload and one warm-up described below. Both observations and their equal-weight means are retained. The six-version cohort has its own 18-load, 930-dispatch, 242,976-position capacity, 180-minute browser ceiling and 240-minute charged-local ceiling; no historical budget is reopened. The [frozen protocol](fresh-baseline-r4-protocol.md), [editor contract](astra-round4-editor.md) and [canonical fresh report](../reports/fresh-baseline-r4-v1/result.json) supply the precise limits, actual observations and completion status. Quality remains adaptive development evidence on exposed tasks, with no new untouched confirmation.

After the first five quality sessions, disk-headroom checks identified large retained model-download caches. A separately bound [maintenance addendum](fresh-profile-maintenance-addendum.md) permits only one exact local-origin IndexedDB blob subtree to be removed from a completed, dedicated browser profile after verified process exit. Responses, grades, telemetry, manifests, browser-version records, browser state and IndexedDB metadata remain preserved and hash checked. The first five profiles were cleaned after the quality prefix completed. Subsequent cleanup occurs after each completed session and before the next model session, consumes the original local allowance and changes neither dispatch counts nor measurement rules. Its late introduction and per-session receipts are separately released in [maintenance evidence](../reports/fresh-baseline-r4-v1/maintenance.json); it is not represented as part of the initial freeze. This does not establish constant OS cache or background host conditions.

## Benchmarks, exposure and scoring

The development source is [Ai2 RLVR-IFeval](https://huggingface.co/datasets/allenai/RLVR-IFeval/tree/47c03c73621c4aab2b824b7818681117d662770e), revision `47c03c73621c4aab2b824b7818681117d662770e`. The fixed development schedule has 32 prompts and 32 instructions; its ordered item identity is `9aa732f4c0dbe06248a93c329299f3fb732a5f148447d3be5a057c93e5fae627`. These prompts were supplied to the editor.

V1 final evaluation uses a selected 128-prompt, 173-instruction subset of [Google Research IFEval](https://github.com/google-research/google-research/tree/e6890f85757dd84e27ca6df2dd30651dafad28e0/instruction_following_eval), revision `e6890f85757dd84e27ca6df2dd30651dafad28e0`. It is not the full 541-prompt benchmark. Selection used task feasibility and instruction coverage before new outputs, with seed 42. The [released item manifest](../reports/ifeval-browser-v1-final/item-ids.json) fixes actual IDs/order; private exclusions mean rerunning a selection heuristic alone need not reconstruct it. Both selected sets cover 18 supported instruction types and eight families. Neither disjoint IDs nor normalized overlap checks establish absence of paraphrase overlap or pretraining exposure.

V1's final prompts are now exposed. The later official-data audit found 129 confirmed-exposed prompts and 215 unresolved-exposure prompts among 344 runtime-feasible items. Its conservative rule admits zero untouched prompts. Historical role assignments, missing records and private filesystem placement are not affirmative evidence of non-exposure. V2 therefore has zero final-quality generations; the new resource pilot adds no quality evaluation.

The unmodified official IFEval checker is wrapped by the frozen grader identity `official_ifeval:d273d53c0d49aa509641885b183d98facd8d2bb2697725f9a2efbaaec52074fd`. Strict prompt accuracy requires all prompt instructions to pass; instruction accuracy divides passing instructions by scheduled instructions. Loose metrics use the official checker alternatives and remain secondary. Failed/truncated outputs remain in the accounting and truncated responses are graded. The `think_tags` policy extracts the answer after a complete leading thinking block; it does not repair answers. Grader calls have a 20-second ceiling and no retries. V1's interval uses 10,000 paired prompt-cluster percentile bootstrap resamples, seed 0, lexicographic item order and linear quantiles, recalculating instruction ratios per resample. It is not an equivalence test.

Quality generation resets the conversation for each prompt: temperature 0, top-p 1, seed 42, thinking disabled, context 4,096, output ceiling 1,024 and 120-second request limit. Each engine load has one warm-up capped at 16 positions. Four injected empty-thinking boundary IDs count toward the output ceiling but not sampled-token usage, leaving at most 1,020 sampled tokens per quality response and 12 per warm-up. A fixed seed does not guarantee identical output across runtime or hardware changes.

## Resource-only pilot

The resource source is [Browser LLM Bench](https://github.com/gufranmirza/browser-llm-bench/tree/b39187b1aff1f218493622d7fcf3cd5d24773b41), revision `b39187b1aff1f218493622d7fcf3cd5d24773b41`, by Gufran Mirza and Arhaan Aggarwal. Its standard repeated-prompt workload is distinct from IFEval. The new protocol schedules:

`pristine → v1 → v2-r1 → v2-r2 → v2-r3 → v2-r3 → v2-r2 → v2-r1 → v1 → pristine`

Every measured resource request repeats this exact public upstream prompt:

> In three short sentences, explain why leaves change color in autumn.

This single repeated workload measures resource behavior under a controlled request. It is not a sample of diverse quality tasks; no private IFEval prompt or generated response is reproduced here.

Each artifact has two sessions with mean ordinal position 5.5. This mirrored order balances a simple linear trend in session position; unequal session durations mean it is not exact balance in elapsed time. It is deterministic, not randomized, and does not remove nonlinear thermal drift, carryover or background activity. The adjacent middle sessions are not more independent because they are adjacent. There is one device/environment and no independent multi-device replication.

Each session has 60 measured requests in three windows of 20, two 90-second loaded-idle gaps, a 15-second baseline phase, 30-second final loaded-idle phase and 15-second recovery phase. It repeats the upstream prompt, resets the conversation before every request, uses temperature 0, top-p 1, seed 42, thinking disabled, context 4,096, a 64-position output ceiling, one 16-position warm-up and the original 60-second request timeout. The corresponding sampled ceilings are 60 and 12 tokens. A fresh dedicated browser profile and empty IndexedDB isolate browser model caches; hash-verified local no-store fetching does not establish a cold operating-system disk cache.

The separately bounded allocation is 10 loads, 10 warm-ups, 600 measured requests, 610 total dispatches and 38,560 reserved output positions; at most 5,400 browser seconds, 7,200 active local seconds, 86,400 calendar seconds and 32 GiB of newly retained artifacts, with at least 8 GiB free. Limits are ceilings, not completion guarantees. No frontier calls, quality reruns, replacement sessions or automatic retries are allocated. All positions, including failures or missing sessions, remain visible. The frozen current browser/device/runtime identity must match between sessions.

## Measurements and analysis

The independent measurement unit is the **browser session**, with two planned observations per artifact. Sixty repetitions of the same prompt within a session are not 60 independent experiments and do not sample instruction-following quality. Publish individual session values and their mean/minimum/maximum; compare descriptive differences to pristine. Do not calculate request-level significance or claim equivalence, a precise population effect, general efficiency, or quality preservation from this pilot. Comparisons requiring missing or invalid measurements remain unavailable.

Each session's throughput is its token total divided by its response-time total. The artifact-level throughput is the **equal-weight arithmetic mean of the two session ratios**, not pooled tokens divided by pooled seconds across sessions. Other metrics are also averaged across the two session values independently. Consequently average throughput and average milliseconds per token need not be reciprocals, especially when the two sessions differ substantially. Mean response latency must not be inverted to reconstruct the published throughput. Both individual values and their range remain visible.

| Quantity | Definition and scope |
| --- | --- |
| Sampled output tokens | Sum of WebLLM completion usage over measured requests; excludes warm-up and four injected boundary IDs, includes a sampled terminating stop when reported. Report every request's actual length and finish reason. |
| Response time | Browser wall time around each completion call, including prefill and decode. Session total is the sum of measured response durations, excluding load, warm-up and idle gaps. Mean response time divides that sum by measured requests. |
| End-to-end output throughput | Measured sampled tokens divided by summed measured response seconds. Milliseconds per output token is the inverse ratio. These are ratios of sums, not a mean of request rates, and are not decode-only throughput. Different output lengths mean different realized work. |
| Load and session time | Reported load duration separately from the profile's total session duration. Full session time includes prescribed baseline/idle/recovery phases and is distinct from summed response time and controller-stage time. |
| Native process footprint | Sum of dedicated Chrome process-tree `ri_phys_footprint`, reported in decimal GB (bytes / 10^9). Peak is sampled maximum during the profile; idle is median after the final active phase; recovery is median during recovery, not an amount of memory freed. It is not globally deduplicated physical RAM; do not add overlapping counters. |
| CPU capacity | Complete dedicated Chrome process-tree CPU intervals normalized by logical CPU count; time-weighted over intervals wholly inside active windows. 100% means the machine's logical CPU capacity under this normalization, not one core. |
| Experimental GPU time | Driver-accounted Chrome command-buffer milliseconds per elapsed second from AGX AppUsage, including browser rendering. It is not shader occupancy, GPU capacity percentage or model-only use; concurrent queues can overlap. Counter/client discontinuities invalidate intervals. |
| GPU-buffer descriptors | Sampled maximum of WebGPU buffer descriptor byte accounting. This is allocation accounting, not measured physical VRAM or residency. |
| WASM address space | Sampled maximum WebAssembly linear-memory byte length. Address space is not physical residency; do not add it to native footprint. |
| Host power and energy | Optional observed CPU/GPU/ANE subsystem estimates across the host, not wall-plug or model-attributed power. Unprivileged capture can leave power unavailable. Preserve original observed interval integration, coverage and baseline semantics; missing power is not zero. |
| Coverage | CPU/GPU/power summary coverage is valid interval duration divided by active-window duration. Boundary-crossing, discontinuous and missing intervals are excluded rather than zero-filled. Publish coverage alongside every available interval metric. Native signal-presence metadata is separate from duration coverage. |

The native merger's energy interval spans its recorded first-active to last-active bounds, which can include between-burst idle gaps. It must not be relabeled as the sum of request-only energy. Its observed five-second pre-run baseline and above-baseline energy remain host-level estimates. Sampling and collection overhead, finite coverage and the single-device schedule limit attribution.

CPU capacity, GPU milliseconds per second and watts are **rates**, not cumulative work or energy. A lower activity or power rate alongside a longer response does not establish less total computation or energy. Interpret rates with response/session duration and signal coverage; do not treat a lower rate as an efficiency gain by itself. The experimental GPU counter is driver-accounted time, not a count of arithmetic operations.

## Integrity, failures and reproducibility

V1 preserved a converter-environment failure and an interrupted final candidate session. The candidate produced 94 outputs before a supervisor reconciliation issue; a separately budgeted continuation generated only the remaining 34. This is a completed manually continued comparison, not an uninterrupted randomized run. Historical timing differences cannot isolate the weight edit.

V2 preserved an initial sandbox failure before any load or generation. It consumed one of four browser attempts, leaving three real candidate evaluations; the fourth proposal slot closed without another Astra call. After all round-3 browser outputs and cleanup completed, offline grading stopped on dataless files before any checker call. Recovery verified 19 copied harness files, restored 171 pinned evaluator payloads, quarantined 347 unavailable bytecode caches and recovered four exact frozen inputs. The complete preflight matched 758/758 frozen inputs. One additional 27.657-second offline grading pass used saved outputs, with zero model loads/generations or editor calls. Earlier failed stages, halt snapshot and original ledgers remain retained.

The new resource pilot stopped after six completed sessions when position 7's integrity preflight timed out while reading an offloaded, protected V2 result file. The failed verification consumed 28.943 seconds but created no position-7 reservation, session directory, model load or generation. An independent ordinary read subsequently recovered the original 10,135 bytes with the exact frozen SHA-256; no reconstruction or overwrite was needed. The stopped root and its six observations remain preserved, including the slower second V2-R3 session. A separately identified continuation completed only the originally undispatched positions 7–10 while retaining spent costs, the original deadline and total ceilings. The recorded gap after position 6 is 1,331.749 seconds; this is not an uninterrupted ten-session run. All ten sessions completed in the original order with 600 measured requests, ten warm-ups, 23,430 sampled tokens and zero generation retries or failed target sequences. Recorded browser/device/runtime identity matched across the sessions; this does not establish unchanged background host load. The complete measurements and continuation provenance are in the [resource report](../reports/resource-all-edits-v1/result.json).

Offline continuation admission also encountered unavailable NumPy payloads, followed by a separate no-load preparation failure while reading a model shard. These are infrastructure failures, not replacement model observations. The pinned NumPy 2.3.5 wheel was extracted to a temporary import overlay without changing the installed environment: 896 members match the installed RECORD digests, and the self-unhashed RECORD member is covered by the exact archive identity. All 897 members are individually hashed. Exact temporary byte caches then verified the 100 deployed model-file paths (36 unique payloads) and 423 frozen source, build and completed-session evidence paths (411 unique payloads). Only unavailable original files may be restored from a matching cached hash; a readable mismatch remains an error. The mutable public report is retained as a snapshot and is excluded from restoration. Temporary cache bytes count against the original retained-data ceiling, and offline recovery and failed preparation time remain charged through the conservative pause accounting. No extra model load or generation is authorized by this recovery.

The reused V2 quality baseline ran Chrome 156.0.8078.80, while the V2 candidates ran Chrome 157.0.8103.39. This prevents an isolated weight-only causal interpretation of the historical development comparison. It does **not** make a newly verified same-environment resource comparison unmatched: the new resource report independently records and checks its current environment. No old frozen report or runtime is rewritten to erase these differences.

The resource pilot executes from a clean publication checkout, with an explicit 38-module source closure and separately hashed new controller. Its 37 inherited Python modules match the public source tree; unrelated local native-backend changes and dormant MPS experiments are excluded from the execution source. The report records the base commit and exact module hashes separately, so the base commit is not presented as containing subsequently added controller code. Model artifacts and private execution evidence remain in their preserved storage locations. Integrity verification and reporting are charged to the new local clock; browser-stage time also includes its bounded preparation and finalization.

Public artifacts include sanitized measurements, IDs, operation arrays, source hashes, methods and executable verification logic. They exclude private prompt/response text, editor packets, authorization, credentials, local machine paths and session transcripts. A hash identifies evidence but does not supply its bytes. The public release supports transformation reconstruction and summary verification; independent regrading of withheld raw outputs, original editor access verification and exact private-environment replay require custodian evidence. No new inference is needed to audit existing summaries.
